# Making Tetra easier to extend, a study

What Truly Modular does, what Tetra already does, and what is worth changing. Written after the
26.1.2 port, from reading the four Truly Modular repositories and measuring Tetra against them.

## 1. Read this before anything else, the licences do not allow the obvious plan

**Modular Item API is under the PolyForm Shield License 1.0.0.** That licence exists to stop one
specific thing: using the software to build something that competes with it. Its words are
"providing any product that competes with the software", and it says that covers a product offered
through a different interface, platform or programming language.

Tetra is a modular item mod. Modular Item API is a modular item api. There is no reading of that
clause where Tetra is not a competing product. So:

* Tetra cannot take code from Modular Item API. Not a class, not a method, not a copied algorithm.
* The three content mods are friendlier, Arsenal is GPL-3.0 and Archery and Armory are MIT, but
  they are addons that depend on the api and are close to useless without it.
* What is not restricted is the design. Ideas, file layouts, and the shape of a data format are not
  what a licence protects. Reading their material json and then writing our own loader is fine.
  Copying their loader is not.

Tetra's own terms cut the other way and are just as binding. They forbid redistributing the project
in its entirety, and forbid code that is fifty percent or more functionally equivalent. A rewrite
that made Tetra into a Modular Item API clone would fail both licences at once, theirs for
competing and Mikael's for equivalence.

**So the answer to "even if it costs a rewrite" is that a rewrite is the one option that is closed.**
Everything worth having here is reachable without one, and section 5 says how.

## 2. What Truly Modular actually does better

Measured, not impressions.

| | Truly Modular | Tetra |
|---|---|---|
| Material definitions | 114 json files | 70 json files |
| Module textures shipped | greyscale plus palette | 268 png files |
| Cost of a material with a new look | one json file | one json file and new art for every module |
| Compat with another mod's tools | generated by scanning them | hand written per mod |
| Authoring tool for non coders | a web app | none |
| Behaviour extension points | 132 registered properties | 95 named effects, behaviour in Tetra's own java |

Three of those matter. The rest is noise.

### 2.1 Greyscale textures with a per material palette

This is the big one. A Truly Modular material carries a colour palette rather than a tint:

```json
"color_palette": {
    "type": "grayscale_map",
    "colors": { "24": "082420", "107": "156355", "190": "2bc7ac", "255": "a4fdf0" },
    "filler": "interpolate"
}
```

Module art is drawn once in greyscale. Each material remaps that greyscale ramp to its own colours,
interpolating the steps it was not given. A new material is one file and no art at all.

Tetra is closer to this than it looks. A material already names a texture class and a tint:

```json
"tints": { "glyph": "iron_glyph", "texture": "iron" },
"textures": [ "metal", "default" ]
```

So a material that fits an existing class already costs one file. The gap is that Tetra's tint is a
single multiply colour over an already coloured texture, which can only shift a look, not define
one. That is why `basic_hammer` ships `log`, `metal`, `obsidian`, `stone` and `warforged` variants,
each in left and right, and why 268 pngs exist. A material that does not resemble one of those five
needs an artist.

### 2.2 Generated compatibility

Their compat document is worth quoting the substance of: they scan another mod's tools, match the
stats, and generate a material from what they find. It is imperfect by their own admission, right
click abilities and on hit effects cannot be detected, and the naming comes out odd. But the
baseline is that an unknown mod's iron equivalent works without anybody writing anything.

Tetra has no equivalent. Every compat material is hand written, which is why compat is a permanent
backlog rather than a solved problem.

### 2.3 An authoring tool

They ship a web app that writes a compat material for somebody who cannot code. That is a
distribution decision more than an architectural one, and it is cheap once the format is stable.

## 3. What Tetra already has, and should not lose

It is worth being clear that Tetra is not the primitive one here. It is already data driven, across
fourteen datapack directories: materials, modules, schematics, improvements, synergies, item
effects, modifier effects, crafting effects, tweaks, tiers, repairs, replacements, actions and
holosphere entries.

The item effect system in particular is a real data language already. `effect/data` holds outcomes,
number providers, vector providers, entity providers and conditions, all resolved from json. That is
the same idea as their property system, arrived at independently, and in the areas it covers it is
comparable.

Tetra's schematic and improvement model is also richer than anything in the Truly Modular data, and
the honing and settling progression has no counterpart there at all. None of that should be
disturbed.

## 4. Where Tetra is genuinely closed

Two places, both real.

**There is no api package.** Nothing in `se.mickelus.tetra` is marked as a surface another mod may
depend on. An addon author has to reach into internals and hope. Compare with a registered property
system where the contract is explicit.

**Effect behaviour is not extensible.** `ItemEffect.get(String)` interns a name into a map, so an
addon can name an effect. The behaviour behind it lives in Tetra's own java, in the handler chains.
So an addon can declare an effect that does nothing, which is worse than not being able to declare
one. The newer `item_effects` data system fixes this for the effects it covers, and the fix is to
widen it, not to replace it.

## 5. What to do, in order

Ranked by value over cost. Each step is worth doing alone, and none needs a rewrite.

1. **Palette driven module textures.** Add a `palette` block to the material format beside the
   existing `tints`, and a greyscale texture class that a module can declare. Materials keep working
   as they are, and a material that supplies a palette gets its own look with no art. This is the
   single change that makes materials cheap, and it slots into `ModularItemModel`, which already
   builds every layer at runtime and already applies a per layer tint. The tint plumbing that took
   most of this session to get right is exactly the plumbing a palette needs.

2. **A material generator.** Walk the item registry at datapack load, find tools that expose a
   `ToolMaterial`, and synthesise a Tetra material from durability, mining level, speed and
   enchantability, backed by the repair item the tool declares. Emit it only where no hand written
   material claims the same item, so authored data always wins. This turns compat from a backlog
   into a default. It also depends on step one, because a generated material has no art.

3. **An api package with a stable surface.** Move the things an addon legitimately needs, effect
   registration, material lookup, module queries, into `se.mickelus.tetra.api`, and treat everything
   else as internal. This costs nothing but discipline and is the prerequisite for anybody building
   on Tetra deliberately rather than by accident.

4. **Data driven effect behaviour.** Widen `item_effects` until a new effect can be declared entirely
   in json, and port the built in effects onto it as they are touched. Do not attempt this as a
   sweep, ninety five effects is not a refactor anybody finishes.

5. **A json schema and generated documentation.** The `schemas` directory already exists at the
   repository root. Filling it out gives editor completion for every datapack author, which is most
   of what their web app provides, at a fraction of the effort.

## 6. What not to do

* Do not copy anything from Modular Item API. Section 1.
* Do not rewrite Tetra as an api plus content mods. That is their shape, it fits a project that
  started there, and reaching it from here means both licences are broken and Tetra's own
  progression systems get discarded on the way.
* Do not start with the effect system. It is the largest surface and the least of the three real
  gaps.

## 7. Where this leaves mutil

Mutil is the shared library and is where the generic half of step three belongs, the data store, the
network layer and the gui toolkit. It is already the right shape for that and needs no modernisation
of its own beyond being documented. Nothing in this study argues for changing it.
